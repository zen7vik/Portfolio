## The problem

The scoring engine is the heart of the platform. Every control change, assessment, and threat-intel update flows through it to recompute a customer's risk. It runs about 72 million risk-scenario calculations a month across 6 production regions, and it had become the platform's least boring service: consumers crashing with out-of-memory errors after hours of uptime, slow customer-facing APIs, and incidents that started somewhere else and ended here.

## The system

Scoring is event-driven. Upstream changes land on a reactor that decides what to rescore, a buffer queue collapses storms of related changes, and consumers assemble inputs for an external FAIR and Monte Carlo scoring API, then aggregate scenario scores up to the entity level. The engine's job is orchestration done well: caching, batching, persistence, and keeping the blast radius small.

The performance program attacked one cause at a time:

- **Memory retention.** A consumer was being killed after roughly ten hours. Bulk deletions loaded 42-column ORM rows just to write a three-field audit log, a per-entity mutex cache never evicted, and an accidental O(n²) array build sat in the loop. Fetching only the needed columns, bounding the cache, and fixing the loop stopped the crashes.
- **Database indexing** on the hot lookup paths that ate CPU during scoring storms.
- **Connection keep-alive with bounded timeouts**, so slow downstream calls stop holding sockets and threads hostage.
- **Cache redesign.** Every TTL now lives in one place. The scoring cache is keyed by a hash of the exact inputs for 24 hours, and a short dedup window collapses control storms before they fan out into simulations.

## Key decisions

- **Dedupe before you scale.** The cheapest simulation is the one you never run. Input-hash caching and buffer dedup bought more headroom than any instance resize.
- **Fix the allocation, not the limit.** The out-of-memory fix was object-shape work measured against the real code path, not a bigger container.
- **Follow the chain.** One incident looked like a database outage in an unrelated service. Tracing it showed five hops: 18K control writes became 19.2M change events, then 46M analytics logs, then 42K scoring messages, then a shared database running out of memory. Fixing the first hop mattered more than the last.

## Outcomes

Comparing May to early July against mid August to September 2026: p95 API latency fell from 604 ms to 281 ms (53% lower) and the server error rate fell 58%, while the engine kept serving 354 tenants across 6 regions.

## What I'd do differently

Consolidate the scoring client so a temporary in-service re-implementation cannot drift from the external API, and add a request-level timeout on every S3 read. One hung read during a what-if simulation taught that lesson the hard way.
