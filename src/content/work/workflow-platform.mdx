## The problem

Our workflow engine ran third-party risk automation: assess a vendor, create issues, send reminders, escalate. Every action was a hand-built node. When a customer wanted to wire in Slack, Jira, or any internal API, the answer was "wait for engineering to build that node." A fixed menu, growing backlog.

The fix sounds simple: add a generic HTTP request node. But a node that makes arbitrary HTTP calls from inside a multi-tenant platform is a security minefield. It needs credentials that analysts can save but never read back, egress that cannot be pointed at our own internal network, and failure semantics that make sense to a non-engineer staring at a workflow run.

## The system

The engine itself is Go on Temporal. A workflow is a JSON graph of typed nodes; a framework-agnostic interpreter walks the graph, and every node stays deterministic by delegating I/O to Temporal activities. Nodes self-register at boot, so adding a node type is one file, not a wiring exercise.

The HTTP node is the deep end of that model:

- **Credentials vault.** Secrets are stored envelope-encrypted in the admin service. The workflow runtime resolves a credential at execution time: fetch ciphertext, decrypt each sensitive field through the auth service, apply it to the outgoing request. No plaintext is ever logged or returned to a client. Analysts pick a credential from a dropdown; nobody, including the builder UI, can read it back.
- **SSRF-hardened egress.** The dialer resolves DNS once, pins the connection to that IP, and rejects private ranges, link-local, and metadata endpoints, with per-credential exact-host allowlists on top. The n8n-style bypass class (rebind after validation) is closed by construction.
- **Response classification.** Every outcome is classified: got an HTTP status means the workflow branches on it like data; no response for security or config reasons means the run halts. That one rule replaced a mess of per-case retry flags.
- **Test panel.** Builders can fire a test request from the editor that runs the identical hardened path as production, seeing exactly what the run would see, secrets still invisible.

Around the node, the platform grew up: node UI is now declared by the backend (layout, actions, data sources) so the frontend renders any future node generically, and an event-driven execution insights pipeline emits per-run metrics behind a feature flag.

## Key decisions

- **Determinism boundary first.** Node logic never does I/O; activities do. Temporal replay stays correct, and the interpreter stays unit-testable with zero Temporal imports.
- **Fail closed everywhere.** Missing tenant context, unresolvable credential, unparseable config: the run stops before a byte leaves the network. The only retries are for outcomes where retrying cannot double-write.
- **Buy the boring part.** Encryption primitives came from our shared security library rather than a local implementation, one audited path instead of two.
- **Backend-declared UI.** Node config schemas live server-side, so shipping a node no longer requires a frontend release.

## Outcomes

The HTTP node was released in July 2026 as a 30-story epic across 6 services, covering the vault, egress hardening, classification, test tooling, and UI. A senior exec summed up the launch: "This is not just a feature, it opens up adding integrations as a configuration." The execution insights layer followed in August 2026.

Over the same summer the platform's production failure rate fell from 12.3% to 3.8% while monthly run volume roughly doubled.

## What I'd do differently

Codegen typed config structs per node instead of validating maps at runtime. And I would design the execution insights schema alongside the node from day one; retrofitting per-node metrics onto historical runs was avoidable work.
